# CFW Social — Lifecycle Flows

How work moves through the CFW Social system: from user intent → agent execution → output production → human approval → scheduled publishing.

---

## Run Lifecycle

A `Run` is a single agent execution. It starts with a user prompt and ends with zero or more `Output`s.

```
┌─────────┐   POST /chat/stream or MCP cfw_run   ┌─────────┐
│  User   │ ────────────────────────────────────▶│  Run    │
│ Intent  │   { workspaceId, agentId, prompt,    │ pending │
│         │     sources, allowedSkills, model }  └────┬────┘
└─────────┘                                          │
                                                     ▼
                                              ┌─────────┐
                                              │  Run    │
                                              │ running │
                                              └────┬────┘
                                                   │
              ┌────────────────────────────────────┼────────────────────────────────────┐
              │                                    │                                    │
              ▼                                    ▼                                    ▼
        ┌─────────┐                          ┌─────────┐                          ┌─────────┐
        │  Run    │                          │  Run    │                          │  Run    │
        │  done   │                          │ failed  │                          │ retry?  │
        └───┬─────┘                          └─────────┘                          └─────────┘
            │
            ├──▶ Output[] created (image/video/audio/doc)
            │
            ├──▶ RunEvent[] persisted (stage, agent.message, tool.call, asset.created, done)
            │
            └──▶ costUsd, tokensIn, tokensOut written to Run row
```

### State definitions

| State | Meaning | Writable by |
|---|---|---|
| `pending` | Run created but not yet dispatched to agent | cfw-social (on create) |
| `running` | Agent loop is actively processing | cfw-agent (on start) |
| `done` | Agent completed successfully, outputs produced | cfw-agent (on completion) |
| `failed` | Agent error or unrecoverable crash | cfw-agent (on error) |

### Idempotency

The `runId` is generated by cfw-social and passed to cfw-agent. If cfw-agent receives a `runId` already in `running` state, it returns `202 Accepted` and the caller can subscribe to the existing SSE stream via `GET /v1/runs/:runId/events`.

### SSE Event Stream

During `running`, cfw-agent emits typed SSE events (v1 contract, frozen):

| Event | Emitted when | Data |
|---|---|---|
| `stage` | Processing phase change | `{ label: "Analyzing sources" }` |
| `agent.message` | LLM produces text | `{ role: "assistant", text: "..." }` |
| `tool.call` | Skill invoked | `{ name: "p-gfx-short", ms: 4200, ok: true }` |
| `asset.created` | Output uploaded to R2 | `{ assetId, mediaId, cdnUrl, mimeType, kind }` |
| `run.ready` | Reviewable output ready | `{ runId }` |
| `done` | Terminal success | `{ tokensIn, tokensOut, costUsd }` |
| `error` | Terminal failure | `{ message: "..." }` |

cfw-social persists every event as a `RunEvent` row with monotonic `seq`. Clients can replay from `?since=<seq>`.

## Output Lifecycle

An `Output` is created when a skill produces a deliverable and cfw-agent calls the `attach_output_to_composition` MCP tool (or equivalent).

```
Skill subprocess
    │
    ▼
Produces file (PNG/MP4/MP3/PDF)
    │
    ▼
uploads to R2 ──▶ R2_KEY_PREFIX_RULE: `${brandId}/${workspaceId|inbox}/${mediaId}.${ext}`
    │
    ▼
cfw-agent emits `asset.created` SSE event
    │
    ▼
cfw-social calls `attach_output_to_composition` MCP tool
    │
    ▼
Output row created:
  runId  → links to parent Run
  kind   → image | video | audio | doc
  cdnUrl → public R2 URL
  mimeType
  metadata → skill-specific metadata blob
```

### Output → Post relationship

An `Output` can be linked to zero or more `Post`s. This happens when:
1. A composition is approved
2. The approval handler creates `Post` rows per target platform
3. Each `Post.outputId` points to the `Output` that serves as the media asset

## Composition Lifecycle

A `Composition` is a type-locked deliverable inside a `Workspace`. It represents the *intent* to create content of a specific type for a specific platform.

```
┌─────────────┐
│   draft     │ ← created by agent or user
└──────┬──────┘
       │
       ▼
┌─────────────┐
│awaiting_approval│ ← agent calls `request_approval` MCP tool
└──────┬──────┘       ApprovalToken generated (signed JWT)
       │
       ├──▶ approved ──▶ scheduled ──▶ published
       │
       └──▶ rejected
```

### State definitions

| State | Meaning | Transition trigger |
|---|---|---|
| `draft` | Composition created, not yet sent for approval | Initial state |
| `awaiting_approval` | Approval token generated, link sent to user | `request_approval` MCP tool |
| `approved` | Human approved via inbox | `inbox/approve` endpoint |
| `scheduled` | Post rows created with `scheduledAt` set | Approval handler or scheduler |
| `published` | Content posted to platform, `publishedAt` set | Platform webhook or direct API |
| `rejected` | Human rejected via inbox | `inbox/reject` endpoint |

### Revision tracking

- `revisionVersion`: current active revision (starts at 1)
- `totalRevisions`: total number of revisions ever generated
- `autoRenamedAt`: timestamp of last auto-rename (if agent regenerated with new title)

## Approval Workflow

### Step 1: Generate approval token

The agent (via cfw-agent loop) calls `request_approval` MCP tool with `workspaceId` and optional `compositionId`.

cfw-social:
1. Creates an `ApprovalToken` row
2. Generates a signed JWT (`token` field)
3. Returns `{ approvalUrl, token, expiresAt, compositionId }`

### Step 2: Deliver to human

The approval URL is delivered via:
- Telegram message (if conversation started there)
- Web inbox (if conversation started in web UI)
- Email (if configured)

### Step 3: Human review

The approval page (served by cfw-social at `/approval/{token}/chat`) is **public** but requires the signed token in the URL. It renders:
- The composition body/caption
- Media previews (from `mediaUrls` or `Output.cdnUrl`)
- Approve / Reject / Chat buttons

The chat endpoint (`/approval/{token}/chat` GET/POST) allows the human to ask questions before deciding.

### Step 4: Human action

| Action | Endpoint | Effect |
|---|---|---|
| **Approve** | `POST /api/v1/inbox/approve` (signed-token auth) | `ApprovalToken.approvedAt` set; `Composition.status` → `approved`; `Post` rows created per platform |
| **Reject** | `POST /api/v1/inbox/reject` (signed-token auth) | `Composition.status` → `rejected` |
| **Revoke** | `POST /api/v1/inbox/revoke` (session auth) | `ApprovalToken.revokedAt` set; token invalidated |

### Token security

- Tokens are signed JWTs with brand-scoped claims
- `expiresAt` defaults to 7 days
- `revokedAt` null until explicitly revoked
- `accessCount` and `ipAddresses` tracked for audit
- Once `approvedAt` is set, the token is considered consumed

## Post Publishing Lifecycle

A `Post` is a concrete content item scheduled for or published to a specific platform.

```
┌─────────┐   approval creates Post rows   ┌───────────┐
│approved │ ──────────────────────────────▶│ scheduled │
│composition│  one Post per platform        └─────┬─────┘
└─────────┘                                        │
                                                   │ scheduler polls
                                                   │ (or webhook pushes)
                                                   ▼
                                            ┌───────────┐
                                            │ publishing │ ← PFM / direct API call in flight
                                            └─────┬─────┘
                                                  │
                       ┌──────────────────────────┼──────────────────────────┐
                       │                          │                          │
                       ▼                          ▼                          ▼
                ┌───────────┐            ┌───────────┐              ┌───────────┐
                │  published  │            │   failed  │              │   draft   │
                │ (success)   │            │ (error)   │              │ (manual)  │
                └───────────┘            └───────────┘              └───────────┘
```

### State definitions

| State | Meaning |
|---|---|
| `draft` | Post row exists but not yet scheduled |
| `scheduled` | `scheduledAt` is set, waiting for publish time |
| `publishing` | Platform API call in flight |
| `published` | Platform confirmed publish, `publishedAt` and `publishedUrl` set |
| `failed` | Platform returned error, `errorMessage` set |

### Scheduling

`PostTiming` rows define optimal posting slots per brand per platform:
- `dayOfWeek`: 0=Sun … 6=Sat
- `timeSlot`: "09:00", "12:30", "18:00"
- `maxPostsPerDay`: default 3
- `priority`: higher = preferred

The scheduler (background worker) queries `Post` rows where `status = 'scheduled' AND scheduledAt <= NOW()`, then dispatches to the appropriate publisher.

### Platform publishing paths

| Platform | Path |
|---|---|
| LinkedIn, Instagram, X, Facebook, Threads, TikTok, YouTube, Pinterest, Bluesky, Google Business | Via PostForMe (`/api/v1/social/connect` + `/api/v1/webhooks/postforme/events`) |
| Direct (future) | Via `PlatformConnection` with `provider = "direct"` and OAuth tokens |

### Webhook updates

PostForMe sends webhook events to `/api/v1/webhooks/postforme/events`. cfw-social updates the matching `Post` row by `pfmPostId`:
- `status` → `published` or `failed`
- `publishedAt` / `publishedUrl`
- `errorMessage`

## Content Source (Repurpose) Lifecycle

`ContentSource` represents brand-level content ingest (YouTube videos, RSS feeds, etc.) that can be repurposed into new compositions.

```
┌──────┐   user submits URL   ┌──────────┐
│  new │ ──────────────────▶│ new      │
└──────┘                      └──────────┘
                                    │
                                    ▼
                              ┌──────────┐
                              │transcribed│ ← background worker: yt-dlp + Whisper
                              └──────────┘
                                    │
                                    ▼
                              ┌──────────┐
                              │composing  │ ← agent generating compositions
                              └──────────┘
                                    │
                                    ▼
                              ┌──────────┐
                              │  done    │ ← compositions created, ready for approval
                              └──────────┘
```

### Status definitions

| Status | Meaning |
|---|---|
| `new` | URL submitted, not yet processed |
| `transcribed` | Transcript extracted (if video/audio) |
| `composing` | Agent is generating compositions from source |
| `done` | All compositions generated |

## Summary: End-to-End Flow

```
1. User creates/joins Brand ──▶ Brand + BrandDna + default Workspace created
2. User connects social accounts ──▶ PlatformConnection rows created
3. User sends prompt (web/chat) ──▶ BrandConversation + ConversationMessage
4. cfw-social creates Run (pending) ──▶ POST /chat/stream to cfw-agent
5. cfw-agent runs agent loop ──▶ Run.status = running
6. Agent picks skills, produces outputs ──▶ Output rows + RunEvent rows
7. Agent proposes composition ──▶ Composition row (draft)
8. Agent requests approval ──▶ ApprovalToken generated
9. Human approves ──▶ Composition.status = approved
10. cfw-social creates Post rows ──▶ Post.status = scheduled
11. Scheduler dispatches to PostForMe ──▶ Post.status = publishing
12. PostForMe webhook confirms ──▶ Post.status = published
```
